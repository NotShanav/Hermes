# Security notes (Beta 0.1: storage, crypto, foreground tracking)

## Primitives (all from maintained crates; nothing custom)
HPKE RFC 9180 Base / DHKEM(X25519,HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 (`hpke` 0.15.1, docs/HPKE.md);
Shamir 2-of-2 over GF(256) (`blahaj` 0.7); Argon2id (`argon2` 0.6) for the Share-A backup passphrase;
Ed25519 (`ed25519-dalek` 3.0) for checkpoint signatures; SHA-256 (`sha2` 0.11); OS RNG (`getrandom` 0.4);
Windows DPAPI via the `windows` crate. The only code of ours that touches secrets is glue: framing, AAD
construction, key-file formats, and the hash-chain layout.

## Record authenticity (your explicit question)
Encryption to a public key proves nothing about who wrote a record: the public key is stored in the database,
so anyone who can write to the database can create a record that decrypts perfectly (test
`forged_rows_made_with_the_public_key_are_not_trusted` does exactly that). HPKE Base mode adds no sender
authenticity. Hermes therefore adds a **separate signing mechanism**, implemented in this release:

* The collector holds an Ed25519 signing key per key set (generated by `init`/`rotate`, stored DPAPI-protected in
  `<id>.signkey`, never in the database, never in the key shares).
* Each flush appends its rows to a **hash chain** (`chain_i = SHA256(chain_{i-1} ‖ seq ‖ ts_us ‖ key_id ‖
  SHA256(payload))`) and signs a **checkpoint** (first/last seq, previous/last chain value, signer id) in the same
  SQLite transaction as the rows. Cost: ~25 µs per flush.
* The verifying key is written into the **USB share file (Share B)**, not trusted from the database. The viewer
  (`hermes check` / `hermes view`) recomputes the chain from the stored rows and checks every signature with the USB key.

| Attack | Detected? |
|---|---|
| Modify a row (ts, payload, key id), swap rows, reorder | Yes: AEAD failure and/or chain mismatch for that checkpoint range |
| Delete a row in the middle | Yes: sequence gap + chain mismatch |
| Insert a forged record (made with the public key) | Yes: reported as unsigned row / chain mismatch |
| Replace the database's verifying key or the checkpoints | Yes: viewer uses the USB key; signatures fail |
| Delete a checkpoint | Yes: link break + unsigned rows |
| Forgery by someone with the disk image but without your Windows login | Yes: cannot produce signatures |
| **Truncate the newest rows and their checkpoints, or restore an older copy of the database** | **No** (tested and pinned as a known limitation) |
| **Malware running as your Windows user** | **No**: it can use DPAPI like the collector, read the signing key, and write validly signed events |
| Rows written before this release (legacy) | Not signed; reported separately |

Proposed hardening (not implemented): (1) rollback/truncation: the viewer records the highest verified
checkpoint on the USB drive (see docs/ANCHOR.md; not implemented) and warns when an archive shows less; (2) a non-exportable
signing key in the TPM via CNG so that even same-user malware cannot copy it (it could still ask the TPM to
sign); (3) a remote timestamp/anchor is ruled out by your "no network" requirement.

## What is and is not protected
Protected: event content and identifying metadata at rest (docs/METADATA.md); history against theft of only the
PC or only the USB; Share A against other Windows users and disk theft; integrity/authenticity against offline
tampering.

## Limitations you should know
1. Malware as your user defeats DPAPI protection of Share A and the signing key; Share B on the USB is then the
   only confidentiality barrier. While the USB is plugged in and the viewer is open, assume the history is exposed
   to such malware.
2. No forward secrecy for history: Share A + Share B of a key set reveal every record sealed to it.
3. Zeroization is best effort: keys/shares use `zeroize`, but copies may exist in library internals, swap or
   hibernation files. No `VirtualLock` yet. The collector holds no decryption key, only the signing seed.
4. Shamir 2-of-2 is no stronger than an XOR split. I could find no independent audit of `blahaj`/`sharks`;
   the reconstruction fingerprint check removes reliance on its correctness for integrity, not on its randomness.
5. `hpke` has no paid third-party audit (docs/HPKE.md). Pinned to 0.15.1 via Cargo.lock; update deliberately.
6. Ciphertext length leaks body size in 256-byte buckets; timestamps leak activity patterns (docs/METADATA.md).
7. The `CHECK` constraints that reject non-sealed payloads are tripwires, not controls.
8. Single collector instance assumed; no inter-process write lock yet.
9. The `test-support` feature of `hermes-crypto` exposes a non-OS-bound protector and legacy sealing; the workspace
   binaries do not enable it and must never.
10. Window titles reaching the archive may contain secrets in applications that are not excluded.
